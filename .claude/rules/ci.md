# CI, the release and the devcontainer

## CI

`.github/workflows/ci.yml` runs NovaTrail's shared checks from `.github`'s shared workflows, pinned to a release of `.github` by SHA with its version beside it (R03 .github), every `uses:` of `.github/workflows/` at the same one, the composite action `toolchain` among them, which Dependabot raises in one pull request, the group `shared-workflows` (Д88 spec; R117): "Secrets" (gitleaks), "DCO", "Documents" — `docs-check-repo` — and "Go", the shared `go.yml`, whose recipes are the go rule, [go.md](go.md) (R13). Beside them run tutor's own jobs, in the `toolchain` stage: "Samples", `just ci-sample-check` (R69), and "Canvas", `just ci-canvas-check` (R76), the eval rule's checks, [eval.md](eval.md). The jobs in the stage take its image, `novatrail-toolchain`, from the cache of GitHub Actions, by the key of the runner and the sha256 of `.devcontainer/Dockerfile`, one entry, the file `novatrail-toolchain.tar`, that only a push to `main` saves (the 2026-11-09 amendment to R31 spec; R42 .github; R117, R120): in `go.yml` the job "Go / toolchain" looks it up and on a miss builds the image once and hands it to the jobs after it by an artifact; "Documents" takes it by `spec`'s `toolchain.sh`; "Samples", which runs no Go, by a copy of the steps of `go.yml`, which on a miss builds the image itself and saves nothing, since no job of `ci.yml` can take an artifact of `go.yml`; "Canvas", which runs Go, by `.github`'s composite action `toolchain`, called before its work and after it with `save: "true"`, which on a miss builds the image and saves it on a push to `main` alone (R49 .github; R133). The jobs of `go.yml` that run Go, and "Canvas" by the action under the check `canvas` in the key, with every `go.sum` of its checkout, `spec/`'s too, take `GOMODCACHE`, `GOCACHE` and `GOLANGCI_LINT_CACHE` from the cache, by the key of the runner, the check, the Dockerfile and `go.sum`: an exact hit is checked by `go mod verify`, and on a miss the newest entry of the same check and Dockerfile comes by the prefix without `go.sum`, its modules dropped and its builds kept; only a push to `main` saves them, so a pull request reads `main`'s (R41 .github, release `v0.1.33`; R120, R133). A move to a new release of `.github` compares the copy of "Samples" with that release's `go.yml`, step by step: a copy that drifts costs a build, not a verdict. A change of the Dockerfile is a miss, so its pull request builds the image from the network and Go with empty caches, and so does the first push to `main` after it; a change of a `go.sum` keeps the builds. The release always builds the stage `toolchain-core` and takes no cache (R18, R36, R47 .github; the 2026-11-16 amendment to R31 spec; R121). "CodeQL / analyze (go)" builds no image: it takes go.dev's archive by `GO_VERSION` and `GO_SHA256_AMD64` of the `toolchain` stage, checked by that sum, so the stage keeps them as `ARG <name>=<value>`, each once, and sets no `GO*` or `CGO_*` in `ENV` but `GOTOOLCHAIN` (R45 .github). The Dockerfile has three stages, the template's: `toolchain-core` — Node, just, Go, buf and golangci-lint —, `toolchain`, built from it, and `devcontainer`. `go.yml` and "Documents" run lint, vuln, licenses and the documents in the core wherever `toolchain` holds more than it, by an entry `novatrail-toolchain-core.tar` of their own (R47 .github); `tutor`'s `toolchain` adds nothing, so every check runs in `toolchain` and the cache keeps one image, and "Samples" and "Canvas" take `toolchain` (R121). A tool the tests alone need goes into `toolchain`, and then the core keeps what the release and those checks run — golangci-lint for `ci-lint` among them (В40 .github). CodeQL, Scorecard and SonarCloud run beside them too, and every pull request runs every check, documents only or not; a merge waits for them all and for `codecov/patch` (R30 spec). Their findings are closed before the next task, by rule 12 of RUN.md. A key-like constant in a test fails "Secrets" over the branch's whole history: write test keys as plain words.

`.github/workflows/eval.yml` runs the eval with the platform's keys for eval from Secret Manager of `infra`, in the GitHub environment `eval`, and only by hand until the keys are there (R90; Д6 of run/DEBT.md).

## The release

A release of tutor comes out by `.github`'s shared `release.yml` after each green merge to `main` that changes what the module is built from: the tag `vX.Y.Z` of the Go module, which api builds from, and its files, which `just release-files` builds from the tree `git archive` writes — the source, the open views of the measurement's tasks and `SHA256SUMS` (R62, R64). `paths` in `release.yml` lists what the module is built from, the files the code embeds with `//go:embed` among them, and `just release-files-test` holds that list to the code. Nobody tags by hand.

## The devcontainer

The container is spec's, as `just new-repo-draft tutor go 3.6 <tag>` builds it from a copy of spec in the scratchpad, never inside the submodule: a move to a tag of spec takes its `.devcontainer/` from there and adds tutor's own differences again — golangci-lint, under GPL-3.0 as an exception named by R12 and run by `just lint` (R13), in the stage `toolchain-core` (R121), and the image of the submodule's contracts that `buf` builds for spec's `sample-check` and `report-check` (R69). Every tool is pinned by exact version, and every archive by its sha256 beside it for each architecture (RULES.md spec, Hard rules). A raise of Go of tutor's own changes, at once, `GO_VERSION` and both `GO_SHA256_*` of the `toolchain-core` stage, never added to `toolchain`, with the sums of go.dev's list checked against the downloaded archives, and the `toolchain` line of `go.mod` (the 2026-11-11 amendment to R12). The `go` line of `.devcontainer/gopls/go.mod` is spec's: as its header says, a repository takes it with its next move to a tag (the 2026-11-12 amendment to R12). A rebuild of the container is the author's step.
